01Executive overview and migration strategy

Role: Hybrid Cloud / VMware-to-AWS Migration Architect. Baseline target is native Amazon EC2 instances, rehosted with AWS Application Migration Service (AWS MGN) and planned with AWS Transform for VMware. Amazon Elastic VMware Service (Amazon EVS), which runs VMware Cloud Foundation inside an Amazon VPC, is a separate relocate option when VMware continuity is a requirement.

  1. Confirm business drivers: datacenter exit, VMware licensing change, risk reduction, modernization, availability, cost and regulatory constraints.
  2. Choose a disposition per application using the 7 Rs: rehost, relocate, replatform, refactor, repurchase, retire or retain.
  3. Agree measurable success criteria: application availability, acceptable downtime, RTO/RPO, performance, security posture, budget and operational ownership.
  4. Align the program to the AWS Migration Acceleration Program (MAP) phases - Assess, Mobilize, Migrate & Modernize - and confirm funding and partner eligibility early.
  5. Use stage gates: discovery accepted → HLD/LLD approved → landing zone ready → pilot passed → wave go/no-go → hypercare closure.
Design assumption: all topology, IP ranges, naming, durations and sample server quantities in this document are illustrative and require client validation.

02Customer workshops and governance

Run cross-functional discovery before selecting the implementation detail. Structure the workshops around the six AWS Cloud Adoption Framework perspectives: business, people, governance, platform, security and operations.

  1. Executive workshop: scope, cost envelope, success outcomes, decision rights, milestone dates, governance and constraints.
  2. VMware workshop: vCenter versions, ESXi clusters, HA/DRS, datastores, VM hardware versions, snapshots, VMware Tools, SAN/NAS and backups.
  3. Application workshop: criticality, owners, inbound/outbound integrations, dependencies, data consistency, cutover windows and vendor support for AWS.
  4. Network workshop: CIDR overlap, VLANs, AWS Direct Connect or Site-to-Site VPN, IPAM, routing, DNS, proxies, ports, latency and throughput.
  5. Security workshop: identity, IAM Identity Center, secrets, KMS encryption, guardrails, monitoring, regulated data and exceptions.
  6. Operations workshop: monitoring, CMDB, patching, backup/restore, incident response, ITSM change and escalation process.
  7. Establish a technical decision forum, architecture review board, steering cadence, daily cross-region delivery sync and client sign-off workflow.

03Current-state discovery and dependency assessment

Establish an authoritative source inventory and reconcile it with the CMDB and AWS Transform.

  1. Export the VM inventory with RVTools or PowerCLI and import it into AWS Transform for VMware, which builds the inventory, dependency map and draft wave plan. Capture VM ID, OS, vCPU, RAM, used/provisioned disk, datastores, network, VMware Tools, hardware version, dependencies, criticality and owner.
  2. Collect utilization over a representative business period - peaks, month-end jobs, seasonal workloads and storage IOPS. Use AWS Migration Evaluator (agentless collector) when you need a business case with right-sized instances and BYOL vs license-included comparisons.
  3. Map application flows: web → application → database, AD/DNS, file shares, SMTP, batch jobs, API endpoints, certificates and licensing endpoints.
  4. Flag domain controllers, clustering, shared disks, physical dependencies, unsupported OS, static IP assumptions, latency-sensitive services and vendor lock-in.
  5. Classify each workload as ready, conditionally ready, blocked or excluded; record remediation and acceptance ownership.
Architect note: AWS Migration Hub and AWS Application Discovery Service closed to new customers on 7 November 2025, with AWS Transform as the recommended replacement. Existing customers can continue to use them.

04AWS landing zone: organization, accounts and governance

Use a governed multi-account foundation before creating production instances.

  1. Deploy AWS Control Tower (or the Landing Zone Accelerator on AWS) on AWS Organizations: management, log archive and audit accounts, plus Security, Infrastructure, Workloads (Prod / Non-prod) and Sandbox organizational units.
  2. Create a network (connectivity) account for Transit Gateway, inspection and DNS, a shared-services account for directory and tooling, and separate production and non-production workload accounts per application domain.
  3. Define naming, tagging (CostCenter, Owner, Environment, Application), allowed Regions and cost-center attribution; enforce them with tag policies and service control policies (SCPs).
  4. Grant access through IAM Identity Center permission sets mapped to directory groups; use temporary elevated access for privileged tasks. Avoid long-lived IAM users and never use the root user for daily work.
  5. Apply guardrails: SCPs (deny leaving the organization, disabling CloudTrail or creating public S3), Control Tower controls and AWS Config rules for tagging, encryption and public exposure.
  6. Provision an organization CloudTrail, AWS Config, Security Hub, GuardDuty, IAM Access Analyzer, AWS Budgets and cost anomaly detection, all delegated to the security and log archive accounts.
  7. Validate Service Quotas and capacity in the target Region: EC2 vCPU limits per instance family, EBS volumes and snapshots, Elastic IPs and MGN replication servers.
Approval gate: client accepts HLD, LLD, the landing-zone security baseline, the cost model and operating responsibilities before any production wave.

05Hybrid network, connectivity and DNS

Preferred example: AWS Direct Connect (with Site-to-Site VPN as backup) into a Transit Gateway in the network account, with routed production and non-production VPCs and a central inspection VPC.

  1. Create a non-overlapping address plan with Amazon VPC IP Address Manager (IPAM), e.g. on-prem 10.10.0.0/16; network/inspection 10.0.0.0/16; prod 10.20.0.0/16; non-prod 10.30.0.0/16; migration staging 10.40.0.0/24.
  2. Build VPCs across at least two Availability Zones with private application subnets, a dedicated staging-area subnet for MGN replication servers, and test and cutover subnets.
  3. Provision Direct Connect (dedicated or hosted connection, Direct Connect gateway, transit VIF) and a Site-to-Site VPN as backup; validate BGP, failover and throughput. Consider AWS Cloud WAN for complex global connectivity.
  4. Attach VPCs to the Transit Gateway with separate route tables for prod, non-prod and shared services; share the Transit Gateway through AWS RAM.
  5. Deploy AWS Network Firewall (or an approved third-party appliance behind Gateway Load Balancer) in the inspection VPC; enforce east-west and north-south traffic with security groups, network ACLs and Firewall Manager policies.
  6. Implement hybrid DNS with Route 53 Resolver inbound and outbound endpoints and forwarding rules shared to workload accounts. Validate AD-integrated DNS and private hosted zones.
  7. Test routes, required ports, MTU (Direct Connect jumbo frames vs VPN), name resolution, application latency and path symmetry before migration. Use VPC Reachability Analyzer to prove paths.

06Identity, security and nonfunctional requirements

AD, DNS, access control and application authentication must remain valid during the hybrid phase.

  1. Inventory Active Directory forests, sites, subnets, service accounts, GPOs, certificates, PKI and DNS dependencies.
  2. For domain controllers, deploy new DCs on EC2 in a new AD site (or extend with AWS Managed Microsoft AD where it fits) and let them replicate, rather than rehosting DCs like normal servers.
  3. Validate Kerberos, LDAP/LDAPS, time synchronization (Amazon Time Sync Service), hybrid DNS and application service accounts.
  4. Enable EBS encryption by default with customer-managed KMS keys, store secrets in AWS Secrets Manager, use Systems Manager Session Manager instead of open RDP/SSH, and centralize findings in Security Hub.
  5. Agree NFR acceptance criteria for latency, IOPS, availability, data integrity, RTO/RPO, retention and operational SLAs.
  6. Prove backup restoration and DR exercises; a successful instance boot is not evidence of application recoverability.

07AWS Transform and Application Migration Service setup

Use current AWS documentation to confirm console labels, the supported OS matrix and network prerequisites; service names and workflows change (the MGN documentation now appears under the AWS Transform MGN name).

  1. Create an AWS Transform for VMware job in the migration account, import the RVTools inventory, review the dependency groups and generate wave plans and target network configuration (CloudFormation, CDK, Terraform or Landing Zone Accelerator output).
  2. Initialize AWS MGN in each target account and Region; this creates the service-linked roles and the default replication settings and launch templates.
  3. Configure the replication settings template: staging-area subnet, replication server instance type, EBS volume type for staging disks, EBS encryption key, data routing over private IP, bandwidth throttling and tags.
  4. Install the AWS Replication Agent on each source VM (agent-based replication is the recommended method; use the MGN connector to install agents at scale). Agentless vCenter replication is no longer available for new deployments.
  5. Use short-lived credentials for agent installation (an IAM role with the AWSApplicationMigrationAgentInstallationPolicy, or temporary credentials), never long-term administrator keys.
  6. Confirm every source server appears in MGN with the expected disks, and reconcile against vCenter and the AWS Transform inventory; troubleshoot omissions.
Architect note: Agent-based replication still needs network paths and change approval on each VM: plan agent installation as its own work package with the server owners.

08Assessment, sizing and cost modeling

Translate discovered utilization into EC2 instance types, EBS volumes and a run-rate the business signs off.

  1. Use AWS Transform and Migration Evaluator outputs for right-sized instance recommendations in the approved Region; price them with the AWS Pricing Calculator.
  2. Size on observed utilization only when the history captures representative peaks; otherwise size as-is and plan a right-sizing pass after migration with explicit risk acceptance.
  3. Evaluate vCPU/RAM, EBS IOPS and throughput (gp3 by default, io2 for demanding databases), network bandwidth, boot mode (BIOS/UEFI), OS support and instance family availability per Availability Zone.
  4. Compare instance families (Intel, AMD, Graviton for compatible Linux workloads), Windows and SQL Server licensing (license-included vs BYOL, Dedicated Hosts where licensing requires), and Savings Plans or Reserved Instances for the steady baseline.
  5. Classify ready / conditional / not ready and assign remediation owners; obtain application owner sign-off on performance assumptions.
  6. Publish the assessment, target mapping table, monthly cost estimate and transition risk.

09Replication setup and monitoring

AWS MGN performs continuous block-level replication from the source server to low-cost replication servers and EBS volumes in the staging subnet; no instance is launched until you test or cut over.

  1. Confirm agent health, staging subnet capacity, replication bandwidth (initial sync volume vs window), target quotas and launch networking.
  2. Start replication and monitor initial sync, then continuous replication: data replication status, lag and backlog in the MGN console and Amazon CloudWatch.
  3. Review each server's EC2 launch template: subnet, instance type (or right-sizing), security groups, IAM instance profile, tags and licensing.
  4. Configure post-launch actions (Systems Manager documents) for common tasks: install the CloudWatch and SSM agents, remove VMware Tools, apply hostname or DNS changes.
  5. Investigate stalled replication, rescans after reboots, disk changes, insufficient upload bandwidth and staging-area capacity.
  6. Keep application and security teams informed of anticipated downtime, final sync timing and expected configuration changes.
Architect note: Replication is not a backup or a rollback guarantee. Keep the source recovery strategy and the cutover data-consistency procedure separate.

10Pilot and test migration

Launch test instances into isolated test subnets so validation never competes with production.

  1. Select a representative set: Windows, Linux, multi-disk, AD-dependent and a dependent application pair.
  2. Launch test instances from MGN into an isolated test subnet or VPC where production names and IPs cannot collide; replication continues during testing.
  3. Validate OS startup, services, network routes, DNS, AD connectivity, load balancer health, certificates, file mounts, SQL access and scheduled jobs.
  4. Test application transactions, performance, security controls and restore procedures; document defects and remediation.
  5. Terminate the test instances, mark the servers as ready for cutover, and collect pilot business acceptance before scaling to waves. If a test fails, revert the server to ready for testing and retest after fixes.

11Wave planning and readiness gates

Group dependent applications by business criticality, coupling and cutover constraints rather than arbitrary VM counts. Model the groups as MGN applications and waves, seeded from the AWS Transform wave plan.

  1. Wave 0: pilot servers; wave 1: low-risk non-production; wave 2: independent internal apps; wave 3: production groups; wave 4: legacy/complex workloads.
  2. For every server record tool/method, source/target account and subnet, owner, dependency group, data volume, change ID, cutover window, validation, rollback and hypercare.
  3. Create an integrated schedule for replication start dates, firewall change approval, DNS work, quota increases and backup onboarding.
  4. Conduct the go/no-go review: target capacity, replication lag, business owner, security, RTO/RPO, cutover bridge and rollback readiness.

12Production cutover runbook

Application-consistent cutover must be rehearsed and approved. Exact order varies by database and application.

  1. Before the window: approved change, sign-offs, rollback checkpoint, current recovery point, replication lag near zero and a readiness bridge.
  2. Announce start; stop batch jobs, scheduled tasks and external integration traffic; quiesce writes using the application/DB owner procedure.
  3. Stop application services (or shut the source VM down) and confirm in MGN that the last changes have replicated - lag zero, no backlog.
  4. Launch cutover instances from MGN and watch the launch and post-launch actions complete.
  5. Validate boot, volumes, IP/DNS, domain membership, certificates, app services, database integration, security and monitoring.
  6. Switch Route 53 records, load balancer targets and integration endpoints; run smoke tests and business transactions; measure response times.
  7. Obtain business sign-off, then finalize the cutover in MGN (this stops replication and removes the staging resources); enable AWS Backup and alarms, enter hypercare and record timestamps.

13Rollback and data consistency

Rollback is a controlled business decision, not an automatic button in AWS MGN.

  1. At the rollback threshold, stop new writes on AWS and declare rollback on the change bridge.
  2. Determine whether the AWS-hosted workload created post-cutover data; define and test a reconciliation/export procedure before production go-live.
  3. Restart the original on-premises service only after confirming there is no dual-write or split-brain risk.
  4. Reverse Route 53, load balancer and integration endpoints; validate data and transaction continuity.
  5. Communicate status, capture the cause, reopen remediation and reschedule after revalidation. Until cutover is finalized, replication can continue for a retry.
Architect note: Do not promise a simple reverse replication to VMware. Keep source VMs (powered off, not deleted) and their backups protected until the agreed acceptance and decommission gates.

14Backup, DR, security and operations handover

Finish with operational resilience, not just migration completion.

  1. Apply AWS Backup plans (tag-based) to the migrated instances, copy to a second Region or account where required, and verify restores with AWS Backup restore testing.
  2. Define the DR architecture from the approved RPO/RTO: Multi-AZ for zone failure, AWS Elastic Disaster Recovery (DRS) or application-native replication for Regional recovery.
  3. Configure the CloudWatch agent, alarms and dashboards, Systems Manager Patch Manager and Inventory, Amazon Inspector and Security Hub posture.
  4. Update the CMDB, DNS/IPAM records, monitoring owners, backup inventory, operational runbooks and support contacts.
  5. Right-size after a representative observation period with AWS Compute Optimizer; commit Savings Plans only to the right-sized baseline; confirm staging resources are gone.
  6. Complete client acceptance, hypercare exit, decommission authorization for the VMware VMs, lessons learned and program closure.

15HLD, LLD, architecture decisions and quality assurance

The architect governs design quality and customer approval; domain leads implement the details.

  1. HLD: current/target diagrams, business drivers, alternatives, NFRs, security, networking, migration strategy, resilience, operations and risks.
  2. LLD: accounts and OUs, CIDRs, Transit Gateway route tables, firewall rules, security groups, Route 53 Resolver rules, instance types, EBS volumes, IAM permission sets, monitoring, backup, guardrails and code module specifications.
  3. Maintain Architecture Decision Records (ADRs): options, benefits, trade-offs, costs, risks, recommendation and approver.
  4. Apply an architecture review checklist (AWS Well-Architected Framework pillars) and ensure every exception has an owner, expiry, compensating controls and approval.
  5. Review Terraform, CloudFormation or CDK modules, remote state and deployment pipelines against the approved landing-zone guardrails.

16Delivery leadership, RAID and steering cadence

Coordinate the US/India engineering workstreams through clear ownership and escalation.

  1. Assign named leads for VMware, Windows/Linux, networking, security, AWS platform, storage/backup, applications/databases and migration execution.
  2. Run daily technical checkpoints and the US/India handover; publish blockers and decisions in a single RAID register.
  3. Run a weekly architecture review and client steering update; escalate blockers with business impact and options, not raw technical logs.
  4. Use scorecards: servers discovered/assessed/replicating/migrated, success rate, critical defects, cost versus forecast, backup compliance.
  5. Close waves only on business acceptance, operational ownership and documentation, not only on running-instance status.

17Example validation commands and infrastructure-as-code

Examples are diagnostic and must be adapted to the customer network and role permissions.

  1. Windows: Test-NetConnection sql.internal -Port 1433; Resolve-DnsName app.internal; Get-Service; Get-NetIPConfiguration.
  2. Linux: ip route; systemctl --failed; df -h; journalctl -p err -n 50; nc -vz database.internal 5432.
  3. AWS CLI: aws mgn describe-source-servers --query "items[].{id:sourceServerID,host:sourceProperties.identificationHints.hostname,state:lifeCycle.state,lag:dataReplicationInfo.lagDuration}" --output table.
  4. AWS CLI: aws ec2 describe-instances --filters Name=tag:Wave,Values=3 --query "Reservations[].Instances[].[InstanceId,State.Name,PrivateIpAddress]" --output table; aws ssm send-command for post-cutover checks at scale.
  5. In IaC reviews verify naming, tagging, IAM, module versions, network guardrails, remote state access, SCP/Config coverage and deployment approval.
  6. In architecture walkthroughs explain migration controls, decision gates and data-consistency trade-offs rather than listing AWS products.

18Architect interview walkthrough and final checklist

Suggested explanation: "I would run discovery workshops, validate the VMware inventory and application dependencies with AWS Transform, design and approve the AWS landing zone, deploy AWS MGN, right-size workloads, pilot replication and isolated test launches, organize business-aligned waves, run approved cutovers with rollback gates, and lead hypercare, security, backup and operations handover."

  1. Be ready to explain AWS MGN versus AWS Elastic Disaster Recovery, and native EC2 versus Amazon EVS.
  2. Describe how the replication agent's continuous block-level replication and the staging area enable a short cutover window, and why quiescing the source affects consistency.
  3. Explain how AD/DNS, routing, firewall rules, database dependencies and application latency influence wave selection.
  4. Explain data reconciliation during rollback and why writing to both source and target is unsafe.
  5. Explain how HLD, LLD, ADRs, NFRs, RACI, RAID and steering reports keep decisions client-controlled.
