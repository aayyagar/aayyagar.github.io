ADCS ESC1, Explained Simply

October 2026 · 6 min read · by Akhilesh Ayyagari

Active Directory Certificate Services (AD CS) is the PKI that quietly issues certificates across a Windows domain. In 2021, researchers at SpecterOps showed that a handful of common misconfigurations in AD CS let an ordinary user escalate straight to Domain Admin. They named them ESC1 through ESC8. ESC1 is the most common, and once you see it, you cannot unsee it.

The one-paragraph version

A certificate proves "I am this identity." If a certificate template lets a low-privileged user (a) request a certificate, (b) write their own name into it, and (c) use it to log on — then that user can request a certificate that says "I am the Domain Administrator" and authenticate as them. That is ESC1.

The three ingredients

ESC1 needs a certificate template with all of these at once:

IngredientWhat it means
Enrollee supplies subjectThe requester chooses who the certificate is for, instead of the CA deciding. This is the flaw.
Client Authentication EKUThe certificate can be used to log on (Client Auth, PKINIT, Smart Card Logon, or Any Purpose).
Low-privileged enrollmentDomain Users (or a broad group) are allowed to request it.

Miss any one and ESC1 does not apply. Have all three on one template and any domain user can become any user.

How the attack plays out

  1. An attacker with a normal account enumerates templates and finds one that is "enrollee supplies subject" + Client Auth + enrollable by Domain Users. Tools like Certify and Certipy do this in one command.
  2. They request a certificate from that template, and in the request they set the subject alternative name to Administrator.
  3. The CA happily issues a valid certificate that says the holder is the Domain Administrator.
  4. They use that certificate to authenticate over Kerberos (PKINIT) and receive a ticket as the Domain Administrator.

No password was cracked. No exploit was dropped. The PKI did exactly what it was configured to do.

Why it is so dangerous: certificates are long-lived and survive a password reset. Even after you discover the breach and reset the real admin's password, an issued ESC1 certificate keeps working until it expires or is revoked.

How to find it

You do not need to run an attack tool to check. The vulnerable combination is readable in the template object. The giveaway attribute is msPKI-Certificate-Name-Flag with the CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT bit (0x1) set, on a template that also has a client-authentication EKU and broad enrollment rights.

# Find templates where the enrollee supplies the subject
Get-ADObject -SearchBase "CN=Certificate Templates,CN=Public Key Services,CN=Services,$((Get-ADRootDSE).configurationNamingContext)" `
  -LDAPFilter "(objectClass=pKICertificateTemplate)" `
  -Properties msPKI-Certificate-Name-Flag, pKIExtendedKeyUsage |
  Where-Object { $_.'msPKI-Certificate-Name-Flag' -band 0x1 }

For a full audit across ESC1–ESC8, run Locksmith or Certify/Certipy in audit mode against a lab you own.

How to fix it

  • Remove "Supply in the request." Set the template to build the subject from Active Directory instead of letting the requester choose. This alone kills ESC1.
  • Require manager approval. Turn on CA certificate-manager approval so a human signs off before issuance.
  • Restrict enrollment. Limit who can request the template to a specific, trusted group rather than Domain Users.
  • Remove unused templates. If a template is published and nobody uses it, unpublish it.

The takeaway

AD CS is Tier 0. A CA that can issue logon certificates is as powerful as a Domain Controller, and its templates deserve the same scrutiny as your admin groups. ESC1 is not an exotic exploit — it is a checkbox left in the wrong state. Find it, fix the template, and you have closed one of the most reliable paths to Domain Admin in a Windows network.
