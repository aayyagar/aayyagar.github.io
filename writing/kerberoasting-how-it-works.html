Kerberoasting: How It Works, How to Stop It

October 2026 · 6 min read · by Akhilesh Ayyagari

Kerberoasting is one of the most reliable attacks in Active Directory because it abuses Kerberos working exactly as designed. Any authenticated domain user can do it, it is quiet, and it often ends with a cracked service-account password that has admin rights. Here is how it works and, more importantly, how to make it fail.

A quick Kerberos refresher

When a user wants to use a service in AD, they ask a Domain Controller for a service ticket (a TGS) for that service. The DC encrypts part of that ticket with the password hash of the account the service runs under. The user's machine then presents the ticket to the service, which can decrypt it because it knows its own password.

The weak link: the DC hands out that ticket to anyone who asks, and part of it is encrypted with the service account's password. If that password is weak, an attacker can crack it offline.

The attack in four steps

  1. An attacker with any domain account asks AD for the accounts that have a Service Principal Name (SPN) set — these are the service accounts.
  2. They request service tickets for those accounts. This is a normal Kerberos operation; it raises no alarms by itself.
  3. They extract the encrypted portion of each ticket and take it offline.
  4. They run a password cracker against it. There is no lockout and no network traffic — they can try billions of guesses on their own hardware. A weak or reused service-account password falls in minutes.

Because service accounts are often old, have non-expiring passwords, and frequently hold elevated rights, a single cracked account can mean a big step toward domain compromise.

Why it is so effective: the attack needs nothing but a normal domain account, generates ordinary-looking Kerberos traffic, and the cracking happens entirely offline where no defense can see it. The whole game is decided by the strength of the service-account password.

How to stop it

You cannot stop users from requesting tickets — that is Kerberos. So you make the cracked ticket worthless by making the password impossible to crack.

1. Use group Managed Service Accounts (gMSA)

This is the real fix. A gMSA has a 120+ character password that Active Directory generates and rotates automatically every 30 days. No human knows it, and it cannot be cracked in any practical time. Migrate service accounts to gMSAs wherever the application supports them.

2. For accounts that cannot be gMSAs, use very long passwords

Where an application forces a traditional account, give it a 25+ character random password. Kerberoasting relies on cracking being feasible; a long random password pushes the cracking time beyond the life of the universe.

3. Remove unnecessary SPNs and privileges

An account only shows up to Kerberoasting if it has an SPN. Audit your SPNs and remove ones that are no longer needed. And no service account should be in Domain Admins — if a cracked service account is just a service account, the damage is contained.

4. Disable RC4 for Kerberos

Attackers prefer RC4-encrypted tickets because they crack faster than AES. Enforcing AES encryption for Kerberos tickets raises the cost of the attack.

How to detect it

The signature is one account requesting many service tickets in a short time, especially with RC4 encryption. In Windows this is event 4769 (a Kerberos service ticket was requested). A detection groups 4769 events by requesting account and flags anyone pulling tickets for many distinct services with RC4 — the fingerprint of a harvest.

SecurityEvent
| where EventID == 4769
| where TicketEncryptionType == "0x17"   // RC4
| where ServiceName !endswith "$" and ServiceName != "krbtgt"
| summarize Services = dcount(ServiceName) by Account, bin(TimeGenerated, 1h)
| where Services >= 10

Tune the threshold to your environment — vulnerability scanners and some legacy apps request many tickets legitimately.

The takeaway

Kerberoasting is not a bug to patch; it is a design property of Kerberos that punishes weak service-account passwords. The defense is equally simple to state: no crackable service-account passwords. Move to gMSAs, use 25+ character passwords where you cannot, strip unneeded SPNs and privileges, and watch event 4769 for the harvest. Do that, and the attack still runs — it just never produces anything useful.
